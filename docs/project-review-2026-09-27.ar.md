**تقرير مراجعة قالب Clean Architecture — 27 سبتمبر 2026**

> هذا تقرير الحالة قبل الإصلاح. التعديلات اللاحقة ومتطلبات الترقية في [تقرير المعالجة](security-remediation-2026-09-28.ar.md).

القالب يمتلك أساساً معمارياً جيداً واختبارات مفيدة، لكنني لا أوصي باعتماده للإنتاج قبل معالجة دورة حياة الجلسات وروابط الاستعادة وحماية مفاتيح التشفير. نجاح الاختبارات الحالية لا يغطي هذه الحالات الأمنية.

المراجعة شملت المشاريع الستة داخل `src`، ومشاريع الاختبار الثلاثة، وإعدادات Docker وCI، وتوليد القالب وتغليفه، والتوثيق. النسخة `nextleapoperations` غير متتبعة في Git وليست جزءاً من الحل الأساسي؛ فُحص أثر وجودها على التغليف، ولم تُجرَ مراجعة مستقلة كاملة لكودها. لم يُختبر خادم إنتاج أو حسابات حقيقية، ولم تُغيَّر شيفرة التطبيق الدائمة.

حُفظ مصدر اختبارات الإثبات في [ReviewProbeTests.cs.txt](review-evidence/ReviewProbeTests.cs.txt) كدليل قابل للمراجعة، وأُزيل الملف المؤقت من مشروع الاختبارات. لإعادة التجربة يُنسخ النص إلى ملف C# داخل مشروع IntegrationTests، ثم يُبنى المشروع ويُشغّل مع `--filter-class '*ReviewProbeTests'`. هذه الاختبارات تتوقع السلوك الحالي المعيب عمداً؛ عند إصلاحه يجب قلب التوقعات إلى السلوك الآمن قبل اعتمادها كاختبارات دائمة.

**ما يستحق الحفاظ عليه**

- اتجاه الاعتماديات واضح، وعزل EF Core داخل Infrastructure مفروض بالاختبارات.
- حالات الاستخدام منظمة في مجلدات مستقلة، والـendpoints صغيرة، والتحويل بين العقود والنماذج صريح.
- استعلامات Todos تفحص المستأجر والمالك معاً. مفاتيح الكاش تشمل المستأجر والمستخدم. لم أجد تجاوزاً مباشراً لهذه الحدود في المسارات التي راجعتها.
- فحص الأدوار وحالة الحساب والمستأجر من قاعدة البيانات يجعل تعطيل الحساب وتغيير الدور مؤثرين في الطلبات التالية.
- رموز التحديث وروابط البريد عشوائية وتُخزن تجزئاتها، وتوجد حماية من استخدام التوكن نفسه بالتزامن بواسطة `xmin`.
- كلمات المرور تستخدم PBKDF2 بملح عشوائي ومقارنة ثابتة الزمن. الملاحظة هنا تتعلق بإدارة دورة الحياة والترقية، وليس باستخدام خوارزمية تجزئة بسيطة غير مناسبة.
- البريد يدخل Outbox ضمن معاملة، مع حجز `SKIP LOCKED`، ومحاولات محدودة وتأخير متزايد، وتنظيف محتوى الرسائل بعد تسويتها.
- رسائل البريد تتحقق من المدخلات، وأجسام HTML ترمّز قيم المستخدم، وسجلات CQRS لا تطبع كلمات المرور أو محتوى الطلبات.
- توجد فهارس فريدة للبريد والتوكنات، وتحويل لتعارضات قاعدة البيانات إلى 409، وقيود تمنع تعديل سجل التدقيق عبر SQL العادي.
- تطبيق migrations تلقائياً محدود ببيئة Development، وإعدادات الإنتاج الحساسة فارغة بدلاً من الاعتماد على أسرار التطوير تلقائياً.

**الملاحظات مرتبة حسب الأولوية**

التصنيف «عالية» يعني أنها تستحق المعالجة قبل الإنتاج؛ لا يعني أن استغلالها متاح دون الشروط المذكورة. «متوسطة» تشمل عيوب الاعتمادية ومقاومة إساءة الاستخدام. رُبطت المواضع بملفات الكود، مع فصل الإثبات العملي عن تحليل الكود.

**R01 — عالية: تسجيل الخروج وإبطال التحديث لا يبطلان Access Token. مثبتة باختبار HTTP.**

الموضع: [PermissionProvider.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Authorization/PermissionProvider.cs:13)، [LogoutUserCommandHandler.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Application/Users/Logout/LogoutUserCommandHandler.cs:36).

الـJWT يحتوي `session_id`، لكن التفويض يفحص المستخدم ودوره وحالة المستأجر فقط، ولا يفحص أن الجلسة ما زالت فعالة. تسجيل الخروج يلغي Refresh Tokens فقط. إعادة تعيين كلمة المرور واكتشاف إعادة استخدام توكن التحديث يعانيان النتيجة نفسها بالنسبة لتوكنات الوصول القائمة.

الإثبات: تسجيل الدخول، ثم `POST users/logout` أعاد 204، ثم `GET users/me` بالتوكن نفسه أعاد 200. عمر الوصول في إعداد التطوير ساعة؛ في الإنتاج تعتمد النافذة على الإعداد الفعلي. استمرار Access Token بعد الإبطال ليس موضحاً بما يكفي في وصف «إنهاء الجلسات».

الأثر: من حصل على Access Token مسروق يستطيع مواصلة استخدام صلاحياته حتى انتهاء التوكن رغم خروج المستخدم أو استعادة حسابه. تعطيل المستخدم نفسه يوقفه بالفعل بسبب فحص `IsActive`، فلا ينبغي الخلط بين الحالتين.

المعالجة: سجل جلسات مستقل يربط `session_id` بالمستخدم والمستأجر، مع فحص الإلغاء والانتهاء لكل طلب؛ أو Security Version للمستخدم مع سياسة منفصلة لإلغاء جلسة واحدة. اربط الإبطال والتدوير وإصدار الجلسات بآلية تزامن مشتركة. تقصير JWT يقلل الضرر ولكنه لا يحقق إبطالاً فورياً وحده.

اختبار القبول: إعادة استخدام Access Token بعد logout وreset واكتشاف replay تُرفض، مع بقاء الجلسة الحالية فقط عند تغيير كلمة المرور إذا كانت هذه هي السياسة المطلوبة.

**R02 — عالية: رابط استعادة سابق يبقى صالحاً بعد تغيير كلمة المرور. مثبتة باختبار HTTP.**

الموضع: [ChangePasswordCommandHandler.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Application/Users/Passwords/ChangePasswordCommandHandler.cs:66)، [ResetPasswordCommandHandler.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Application/Users/Passwords/ResetPasswordCommandHandler.cs:37).

تغيير كلمة المرور لا يبطل `UserToken` الخاص بإعادة التعيين، وإعادة التعيين تستهلك التوكن المقدم فقط. لا يوجد Security Stamp يربط صلاحية الرابط بحالة بيانات الدخول عند إصداره.

الإثبات: طلب رابط استعادة، ثم تغيير كلمة المرور عبر `users/me/password`، ثم استخدام الرابط السابق لتعيين كلمة مرور ثالثة؛ نجحت العمليتان وأعادتا 204.

الأثر: من تسرب إليه رابط ما زال ضمن مدة الساعة يستطيع استعادة السيطرة حتى بعد تغيير المستخدم كلمة مروره. يحتاج الاستغلال إلى امتلاك الرابط؛ لا يسمح بإنشاء رابط صحيح بالتخمين.

المعالجة: إبطال كل رموز PasswordReset القائمة عند تغيير أو إعادة تعيين كلمة المرور ضمن المعاملة نفسها، وربط الرموز بإصدار أمني يتغير عند تعديل بيانات الدخول. أرسل إشعاراً أمنياً أيضاً بعد إعادة التعيين، كما يحدث حالياً بعد التغيير العادي.

**R03 — عالية عند تسريب قاعدة البيانات: مفاتيح تشفير البريد مخزنة دون تغليف تشفيري. مثبتة بفحص قاعدة الاختبار.**

الموضع: [EmailServiceCollectionExtensions.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Email/EmailServiceCollectionExtensions.cs:25).

يستخدم المشروع `PersistKeysToDbContext` دون إعداد `ProtectKeysWithCertificate` أو آلية مماثلة. ثبت وجود `masterKey` غير مغلف داخل XML في قاعدة الاختبار. لم تُطبع قيم المفاتيح في المخرجات.

الأثر: نسخة قاعدة بيانات تتضمن key ring ورسائل Outbox المعلقة تكفي لفك محتواها، بما فيه روابط الدعوة والاستعادة. تشفير payload في هذه الحالة لا يعزل الرسائل عن من يستطيع قراءة القاعدة كاملة. الرسائل المنتهية التي مُسح محتواها لا ينطبق عليها استرجاع المحتوى من الصف الحالي.

المعالجة: تشفير key ring بشهادة أو بمفتاح موجود خارج قاعدة البيانات ونسخها الاحتياطية، مع صلاحيات محدودة وخطة تدوير واستعادة. تشفير القرص وحده لا يحمي من تسريب منطقي لقاعدة البيانات.

هذا السلوك موثق لدى Microsoft: تحديد مخزن مفاتيح صريح يلغي آلية التشفير الافتراضية أثناء التخزين ما لم تُضبط بديلة. [توثيق Microsoft](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-encryption-at-rest?view=aspnetcore-10.0).

**R04 — متوسطة: إصدار روابط الاستعادة غير محمي من سباق الطلبات.**

الإثبات العملي: اختبار HTTP مع حاجز تزامن عند قراءة الرموز السابقة جعل طلبَي forgot-password يقرآن قبل الإدخال؛ أعاد كلاهما 202، ووُجد رمزان جديدان غير مستهلكين. الحاجز يفرض ترتيباً ممكناً للطلبات ولا يبدّل منطق التخزين أو الإصدار.

الموضع: [UserTokenIssuer.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Application/Users/UserTokenIssuer.cs:25)، [UserTokenConfiguration.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Users/UserTokenConfiguration.cs:21).

المنطق يقرأ الرموز القابلة للاستخدام، يستهلكها، ثم يضيف رمزاً جديداً. إذا قرأ طلبان القائمة الفارغة قبل إدخال أي منهما، يستطيع كلاهما إنشاء رمز صالح. فهرس `(UserId, Purpose)` غير فريد، و`xmin` يحمي تعديل الصف نفسه ولا يمنع إدخال صفين مختلفين.

الأثر: قاعدة «الرابط الأحدث فقط صالح» لا تتحقق دائماً. وبالاقتران مع R02 قد يبقى رابط آخر صالحاً بعد اكتمال استعادة كلمة المرور. لا يكفي امتلاك عنوان البريد وحده لاستغلال تغيير كلمة المرور؛ يلزم الحصول على أحد الروابط.

المعالجة: قفل صف المستخدم أو قفل منطقي للمستخدم والغرض قبل القراءة والإصدار، على أن تتشارك عمليات الإصدار والاستهلاك وتغيير كلمة المرور السياسة نفسها. أضف ضماناً على مستوى قاعدة البيانات لعدد الرموز غير المستهلكة، مع تسوية المنتهية بدلاً من فهرس يعتمد على الوقت الحالي.

**R05 — متوسطة: محدد الطلبات يعمل بعد التفويض، فلا يحمي استعلامات الصلاحيات من الإغراق.**

الإثبات العملي: إعداد الحصة العالمية إلى طلب واحد، ثم إرسال ثلاثة طلبات متتابعة من Member إلى مسار tenants؛ أعادت الطلبات الثلاثة 403 بدلاً من تفعيل 429 بعد تجاوز الحصة.

الموضع: [Program.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Api/Program.cs:68)، [PermissionAuthorizationHandler.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Authorization/PermissionAuthorizationHandler.cs:24).

الترتيب الحالي هو Authentication ثم Authorization ثم RateLimiter. الطلب المرفوض بـ401/403 لا يصل للمحدد؛ والطلب المقبول ينفذ استعلام الصلاحيات قبل أن يعرف المحدد أنه تجاوز الحصة. حساب منخفض الصلاحية يستطيع تكرار استدعاء مسار إدارة غير مسموح وإجبار قاعدة البيانات على فحص دوره كل مرة.

المعالجة: ضع الحد المبني على المستخدم بعد Authentication وقبل Authorization، وأضف حداً أولياً حسب IP عند البوابة أو قبل العمل المكلف. مرر `RequestAborted` لفحص الصلاحيات. عند تعدد النسخ، وضّح أن العداد الحالي محلي لكل نسخة.

**R06 — متوسطة، مشروطة بإعداد خاطئ: قيمة SMTP رقمية غير معروفة تتجاوز اشتراط TLS.**

الإثبات العملي: اجتاز `(SmtpSecurityMode)999` التحقق في بيئة Production مع تفعيل العامل. التحول إلى `None` ثبت بقراءة فرع المحول؛ لم تُجرَ محاولة إرسال SMTP إنتاجية غير مشفرة.

الموضع: [SmtpOptions.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Email/SmtpOptions.cs:67)، [SmtpEmailSender.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Email/SmtpEmailSender.cs:67).

التحقق يمنع `None` خارج Development، لكنه لا يرفض القيم غير المعرفة مثل `999`. محول الإرسال يعامل كل قيمة غير معروفة على أنها `SecureSocketOptions.None`.

الأثر: إعداد رقمي خاطئ يمكن أن يعطل TLS بصمت؛ إذا قبل الخادم الاتصال غير المشفر، قد يعبر محتوى الرسائل والروابط دون حماية النقل. ليس هذا مساراً يسمح لمستخدم API عادي بتغيير الإعدادات.

المعالجة: `Enum.IsDefined`، والسماح حصراً بـStartTls أوSslOnConnect في الإنتاج، ورفض القيمة غير المعروفة في المحول بدلاً من fallback غير آمن. اختبر الربط من متغير بيئة رقمي، لا القيم المعروفة فقط.

**R07 — عالية عند إتاحة المنافذ للشبكة: بيئة التطوير منشورة على جميع واجهات الجهاز. خطر إعدادات مؤكد؛ لم تُختبر قابلية الوصول من جهاز خارجي.**

الموضع: [docker-compose.yml](D:/Development27/Milan/clean-architecture/docker-compose.yml:14)، [docker-compose.override.yml](D:/Development27/Milan/clean-architecture/docker-compose.override.yml:5)، [appsettings.Development.json](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Api/appsettings.Development.json:28).

الأثر يعتمد على جدار الحماية والشبكة: إن كانت هذه المنافذ متاحة للغير، قد تُكشف رسائل الاستعادة أو قاعدة البيانات أو حساب الإدارة. وجود بيانات تجريبية في ملف Development ليس وحده دليلاً على تسريب سر إنتاج؛ المشكلة في تعريض هذه البيئة للغير.

المعالجة: اربط منافذ التطوير بـloopback، وأضف ملف نشر إنتاج منفصلاً مع TLS وأسرار خاصة وصلاحيات قاعدة بيانات محدودة. لا تستخدم superuser لتشغيل التطبيق في الإنتاج. [سلوك نشر المنافذ في Docker](https://docs.docker.com/engine/network/port-publishing/).

**R08 — متوسطة: التغليف يضم ملفات محلية غير مقصودة، بما فيها مشروع كامل. مثبت بتقييم MSBuild.**

`GET todos` يحمل جميع عناصر المستخدم إلى الذاكرة. `Labels` يتحقق من عدم كونها null فقط، دون عدد أقصى أو طول أقصى للعنصر. كلمة مرور الدخول لا تملك الحد الأقصى الموجود عند إنشاء كلمة المرور. لا يعني ذلك أن جسم HTTP غير محدود إطلاقاً؛ توجد حدود الخادم العامة، لكنها أكبر وأقل تخصيصاً من حدود المجال المطلوبة.

المعالجة: pagination بحد أعلى، وترتيب مستقر، وحدود لعدد Labels وطولها وطول كلمات المرور والتوكنات، وحجم الطلب. راجع أيضاً overflow في `(page - 1) * pageSize` للقيم الكبيرة المقبولة حالياً، أو استخدم cursor pagination عند الحاجة.

**R10 — متوسطة عند تعدد النسخ: إبطال كاش Todos محلي، وقد تستمر قراءة بيانات قديمة. تحليل كود موثّق بسلوك المكتبة.**

المعالجة: حدّد سياسة الاتساق صراحة. أبسط اختيار للقالب إزالة كاش التفاصيل ما لم تثبت الحاجة إليه؛ وإلا استخدم مدة محلية قصيرة وإبطالاً بين النسخ أو versioned keys. إضافة Redis وحدها لا تزيل تلقائياً الكاش المحلي على بقية النسخ. **R11 — متوسطة تشغيلية: صحة البريد قد تظهر سليمة أثناء تعطل التسليم. تحليل كود.**

**ملاحظات هندسية إضافية لتطوير القالب**

1. **وحّد سياسة الهوية.** التنفيذ الحالي مخصص رغم استخدام بدائيات تشفير موثوقة. دراسة استخدام ASP.NET Core Identity لعمليات الحسابات وSecurity Stamp وتنسيق PasswordHasher قابل للترقية ستقلل مساحة الكود الأمني المملوك. يمكن الإبقاء على طبقات المشروع وعقوده. لا توجد حاجة لإعادة بناء المعمارية كلها لتحقيق ذلك.
2. **أضف MFA للمديرين وإدارة جلسات فعلية.** واجهة لعرض الجلسات وإلغائها، وإعادة تحقق للعمليات الحساسة، وعمر مطلق للجلسة. التحديث الحالي يجدد سبعة أيام من كل تدوير، فيمكن أن يستمر بلا حد مطلق طالما استُخدم.
3. **حسّن منع إساءة استخدام الاستعادة.** محدد المصدر وحده لا يمنع إغراق صندوق مستخدم عبر مصادر متعددة أو إبطال رابط المستخدم مراراً. أضف تهدئة بحسب الحساب مع نفس الاستجابة العامة، واختبر التوقيت عند ضغط قاعدة البيانات. حد الثانية الحالية ليس ضماناً لإخفاء فروق تزيد على ثانية. كشف الحساب بعد lockout موثق كقرار مقصود في `docs/security.md`، وليس اكتشافاً جديداً؛ يمكن تجنب اختلاف الرسالة العامة مع إبقاء المنع داخلياً.
4. **اجعل أحداث المجال واضحة الضمانات.** في [ApplicationDbContext.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/Database/ApplicationDbContext.cs:46) تُمسح الأحداث قبل الحفظ وتُرسل بعده، وبنطاق DI جديد في [DomainEventsDispatcher.cs](D:/Development27/Milan/clean-architecture/src/CleanArchitecture.Infrastructure/DomainEvents/DomainEventsDispatcher.cs:18). خارج معاملة صريحة قد ينجح حفظ البيانات ويفشل المعالج، فيرى العميل فشلاً رغم نجاح التعديل. داخل المعاملة لا يشارك النطاق الجديد سياقها. المعالج الحالي يسجل رسالة فقط؛ الخطر الأكبر عند إضافة آثار جانبية. استخدم معالجات متسقة داخل المعاملة للأعمال الداخلية، وOutbox مستقلاً للتكاملات والآثار الخارجية.
5. **وسّع حماية التزامن إلى مستوى العملية.** وجود `xmin` على التوكن لا يكفي لكل المسارات. اختبر login متزامناً مع reset، وrefresh مع revoke، وتغيير دورين إداريين بالتزامن، وبداية عدة نسخ مع bootstrap. لا يوجد ضمان ذري لـ«بقاء مدير واحد على الأقل»، كما لا يوجد قيد وحيد للمستأجر المنصي. هذه حالات تحتاج اختبارات حتمية قبل إعلان ضمانها.
6. **أكمل عقد OpenAPI.** كثير من الـendpoints يرجع `IResult` عبر `Match` دون `Produces`/TypedResults يصف عقود النجاح والفشل بدقة. محول الأمن يضيف Bearer على مستوى المستند كله، بما فيه المسارات المجهولة. أضف security override لها، وDTOs للاستجابات وأمثلة وخرائط أكواد الأخطاء. احتفظ باسم الحقل في validation errors؛ التحويل الحالي يحتفظ بالكود والوصف ويهمل `PropertyName`.
7. **وحّد الأخطاء خارج handlers.** رفض Authentication/Authorization و429 وأخطاء JSON لا يمر بالضرورة عبر `CustomResults`. اختبر وجود `code` و`correlationId` وContent-Type صحيح لهذه الحالات أيضاً، وأضف `Retry-After` للرفض بالحد.
8. **جهّز ملف إنتاج قابل للمراجعة.** TLS عند reverse proxy مع قائمة Trusted Proxies موثقة، وصلاحيات DB تشغيل منفصلة عن migrations، ومراقبة ونسخ احتياطي مع اختبار استعادة، وتدوير JWT وData Protection. عدم وجود HTTPS redirection داخل التطبيق ليس وحده ثغرة إن كان TLS مفروضاً أمامه؛ القالب يحتاج عقد نشر يثبت ذلك.
9. **قوِّ CI وسلسلة الاعتماديات.** أضف lock files وlocked restore، وفحص الحزم الدوري، وsecret scanning، وفحص صور الحاويات وSBOM، وتثبيت الصور/actions بإصدارات أو digests مُدارة. فعّل رفع نتائج الاختبارات والتغطية لمساعدة المراجعة. لا حاجة لشراء مكونات لتحقيق ذلك.
10. **أكمل التوزيع والتراخيص.** لا يوجد ملف LICENSE في جذر المشروع الذي راجعته؛ أضف ترخيص المشروع وإشعارات الاعتماديات وقائمة تراخيص مُراجعة، بما فيها أدوات التشغيل الاختيارية مثل Seq. لم تُنفّذ مراجعة تراخيص قانونية أو تحقق شامل لشروط الخدمات ضمن هذه المراجعة.
11. **احمِ سكربت التهيئة.** [init-project.ps1](D:/Development27/Milan/clean-architecture/scripts/init-project.ps1:38) يحذف محتويات المستودع عدا `.git` بعد التوليد دون تحقق برمجي من نظافة Git أو نجاح بناء الناتج. التعليق الذي يطلب commit/stash لا يحمي الملفات غير المتتبعة أو المستثناة. أضف فحصاً مسبقاً ونسخة احتياطية وقائمة ملفات ودعم dry-run، ولا تحذف المصدر قبل التحقق من الناتج. لم يُشغّل السكربت أثناء المراجعة.
12. **اجعل القالب أصغر وأسهل للتخصيص.** احتفظ بالطبقات الحالية، وأضف خيارات توليد واضحة لاختيار المثال Todos والمراقبة والبريد حيث يناسب ذلك. انقل المشروعات الناتجة خارج مجلد المصدر. لا أوصي بإضافة Microservices أو Event Sourcing أو إطار CQRS أكبر دون حاجة فعلية.

**حدود الاستنتاج**

هذه مراجعة كود وإعدادات مع اختبارات محلية، وليست شهادة بخلو المنتج من الثغرات. لم يظهر SQL Injection مباشر في الاستعلامات المفحوصة؛ مواضع SQL الخام تستخدم معاملات للقيم. لم يُثبت تجاوز عام لعزل المستأجرين أو تصعيد دور عبر المسارات الحالية. لا أعدّ غياب MFA أو عدم استخدام Identity وحدهما ثغرة مثبتة، بل فرصاً لتقليل المخاطر وتحسين القالب.

النتيجة العملية: حافظ على الأساس المعماري والاختبارات وصندوق البريد الحالي، وعالج ضمانات الهوية والتشغيل أولاً. هذه التغييرات ستعطي قيمة أكبر من زيادة عدد الطبقات أو المكتبات.
